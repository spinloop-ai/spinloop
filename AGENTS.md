# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`spinloop` is a Go CLI that configures a coding agent — a **harness** — to use a model provider, by deep-merging provider settings into that harness's config. Three harnesses are supported: [opencode](https://opencode.ai) (config under `${XDG_CONFIG_HOME:-$HOME/.config}/opencode`), [Pi](https://github.com/earendil-works/pi) (`~/.pi/agent/models.json`), and [lucinate](https://github.com/lucinate-ai/lucinate) (`~/.lucinate/connections.json`). The harness is chosen at runtime — never baked into a Spinloop file — so the same selection applies to any of them.

## Commands

```sh
go test ./...                  # run the suite
go test ./... -cover           # with coverage (keep total >= 80%)
go vet ./...                   # vet
go build -o spinloop ./cmd/spinloop   # build the CLI binary
gofmt -w ./...                 # format
```

Run a single test: `go test -run TestWriteConfig_Idempotent ./...`

## Layout

The binary lives under `cmd/`; the domain logic is split into `internal/` packages so each concern is isolated and independently testable.

- `cmd/spinloop/commands.go` + `main.go` — the Cobra command tree and, beside it, the command bodies. `newRootCmd` builds a fresh tree per invocation (so a value parsed into one run's flags can never leak into the next), `execCmd(c, args)` is the seam the suite uses to run a command the way the tree does, and thin `cmdX` shims route the suite's direct calls through it. Every command's flags live on its own pflag `FlagSet` (registration in the constructor, parsing by the tree — except `harness`, below); `registerSelectionFlags` is what `add`/`remove` share, registering long and short forms against the same vars with the chosen harness name bound separately so it never leaks into a `Selection`. `main` prints user-facing errors and, when the process is invoked as the completion engine, gives it no stderr (see `complete.go`). Each command's `Long` field is its user-facing description, what `<cmd> --help` prints first (ported from the old hand-written `usage()`); keep it in sync when a command's behaviour changes. `add` and `apply` share `applySelection`, the core that writes one provider selection; `remove` and `unapply` share `removeSelection`, its inverse. Both resolve the active harness (`harness.Resolve`) and route through it. `show` reports the active harness's current config via `harness.State` (the same read `export` reconstructs a Spinloop from). `serve` is harness-agnostic (it launches `llama-server`, not a config write). `harness` runs with `DisableFlagParsing` — it parses the command's own flag set itself, token by token, because a leading positional that names a Spinloop is consumed, a `--` opts out, and everything after the hand-off forwards byte-for-byte; the flags are registered on the command's flag set precisely so parsing and the completion surface read the same registry. It launches the active harness (forwarding trailing args), or manages the stored default with `--get`/`--set`; its `--spinloop`/`-O` routes through the same `applySelection` before launching, so a launch can configure the harness first. That flag's value is optional (`spinloopPathFlag` is a `pflag.Value` whose `NoOptDefVal` is `"true"`, mapped to the empty path) — bare it means the default `./Spinloop`, so a path has to be attached (`--spinloop=<path>`), since positional args belong to the harness; the exception is a *leading* positional that names a Spinloop, which is applied and not forwarded (see "Alias registry" below). `alias`/`unalias` manage the registry that lets a name stand in for a path, and `writeAliases` renders it for both `alias --list` and `show`. Tests: `main_test.go` (add/remove/list/show), `apply_test.go` (`apply`/`unapply`/`export`), `harness_test.go` (the `harness` command, `show`, and Pi-routed add/export/remove), `serve_test.go`, `alias_test.go`, `flagparse_test.go` (pflag parse forms), `viper_test.go` (`SPINLOOP_*` precedence), `complete_test.go`.
- `cmd/spinloop/serve.go` — the `serve` command: `engineFor` and the `serveEngine` table, the binary lookups (`llamaServerBinary`, `resolveOMLXBinary` — PATH then the `/Applications/oMLX.app` bundle), the Spinloop→flags mappings (`llamacppServeParams`/`omlxServeParams`/`bindAddressParams`), and the helpers `remote.go` shares (`resolvePresetPath`, `isModelPath`, `hostPortFromURL`).
- `cmd/spinloop/complete.go` — tab completion. `spinloop completion <bash|zsh|powershell>` prints the script the CLI framework (Cobra) generates for the live command tree; the script hands the words typed so far to the hidden `spinloop __complete` (the framework's engine) and inserts whatever comes back, so the candidates never differ between shells. The engine completes command names, subcommands, and flag names in both forms straight off the tree — there is no second table of the surface that could drift — and `complete.go` supplies the value half: the per-slot candidate functions (`aliasSlot`, `aliasOnlySlot`, `keepSlot`, …) as `ValidArgsFunction`s, and per-flag value completions (`--provider` from the resolved catalogue honouring a `--providers` already on the line, `--model` live from discovery, `--harness`, `--log-level`), with `defaultFlagCompletions` giving every other value flag the boring-but-correct "no candidates, no paths". `harnessSlot` completes `harness` lines: the command's `DisableFlagParsing` means the engine sends it every word unparsed, attached flag values included. The protocol is the framework's: candidate lines (descriptions ride along tab-separated) and a final `:0`/`:4` directive saying whether filesystem paths belong; it never returns an error. The silence guarantee has two halves — `main` points the process's stderr at devnull when this process is the engine, and the root's error stream is discarded, so an unreadable config, an unloadable catalogue, or nonsense input all mean "no candidates" without a spew over the prompt. `TestCompletionCoversTree` walks the tree itself to verify the surface, and `complete_test.go` drives the engine through the real `__complete`.
- `internal/config` — spinloop's own config file, `${XDG_CONFIG_HOME:-~/.config}/spinloop/config.json`: the default-harness preference and the Spinloop alias registry. A **leaf package** — stdlib imports only, and it must stay that way (in particular it must never import `internal/spinloop` to parse a Spinloop), because that is what lets `readSpinloop` resolve a name without dragging in the harness abstraction. Every write goes through `Update`, a read-modify-write of the whole document; unknown top-level keys round-trip through `File.extra`.
- `internal/spinloop` — the `Spinloop` file format and the shared `Selection` type: a flat, Dockerfile-style description of one provider selection (`PROVIDER`/`MODEL`/`ALIAS`/`CONTEXT`/`OUTPUT`/`BASEURL`/`PRESET`/`REMOTE`). `Parse` reads it into a `Selection` (keywords case-insensitive via `canonicalKeyword`, UPPERCASE canonical, `#` comments); `Format` renders one back out for `export`. `apply` defaults to `./Spinloop` (`spinloop.DefaultFile`). The harness is deliberately **not** a keyword — it is a runtime choice, so a Spinloop stays portable. This package stays a pure grammar leaf — no I/O, no `spinloopsrc` import — the CLI layer does the reading.
- `internal/spinloopsrc` — resolves and fetches a Spinloop-family reference (the Spinloop path, `PRESET`, or a path-form `REMOTE`) that may be a local path or an `http(s)` URL: `IsURL`, `Resolve` (a relative reference joins against a local directory or resolves as a relative URL reference depending on what named it — absolute wins regardless), and `Fetch` (`os.ReadFile` locally, a bounded `http.Client` GET remotely — fixed timeout, 1 MiB response cap, a 404 wrapped in `ErrNotFound` so callers that already tolerate a missing local file can tolerate its URL equivalent the same way with `errors.Is`). Every call site that resolves one of these references goes through here, so the URL-vs-local dispatch lives in exactly one place.
- `internal/harness` — the harness abstraction. The `Harness` interface (`Name`/`Command`/`ConfigPath`/`Apply`/`Remove`/`State`), a `registry` of the opencode, pi and lucinate adapters (`adapters.go`, which wrap `catalog` + `opencode`/`pi`/`lucinate` + `contextsize`), runtime selection via `Resolve` with precedence **`--harness`/`-H` flag > `SPINLOOP_HARNESS` env > stored preference > opencode**, and preference load/save (`LoadPreference`/`SavePreference`), which delegate to `internal/config` — that package, not this one, owns the config file. **Start here when adding another harness:** implement the interface and register it.
- `internal/catalog` — the embedded provider catalogue (`//go:embed providers.yaml`), its types, and the two block builders (`apiKeyOptional` marks a provider that also works unauthenticated — `llamacpp` names both a keyless local server and the authenticated remote deployment — so the Pi builder writes its keyless placeholder instead of a `$VAR` that resolves to nothing; every other provider keeps the reference, which Pi resolves at run time): `BuildProviderBlock` turns a provider+model selection into an opencode provider block; `BuildPiProvider` turns the same into a Pi provider entry. The catalogue can be overridden at runtime via the `--providers` flag or `SPINLOOP_PROVIDERS` env var (flag > env > embedded; see `ResolveCatalogPath`/`LoadFrom`). `providers.yaml` lives here.
- `internal/opencode` — opencode config IO: JSONC read/merge/write, env/key resolution, JSON-Pointer helpers. `LoadConfigState` reads the config back (configured providers, their model keys, the default model, context/output limits) for `export`.
- `internal/pi` — Pi config IO: resolves `~/.pi/agent/models.json` (note: `~/.pi/agent/`, **not** XDG), deep-merges one managed provider entry into it preserving everything else (other providers, unknown fields), `Remove`, and reads provider state back for `export`. Written `0600`.
- `internal/lucinate` — lucinate config IO: resolves `~/.lucinate/connections.json` (`$LUCINATE_DATA_DIR` override, **not** XDG), merges one managed OpenAI-compatible connection into it preserving everything else (sibling connections, unknown fields), keyed by a deterministic id (`spinloop:<providerId>`), and points the store's `defaultId` at it so lucinate opens onto the configured model. `Remove` deletes that connection (and clears `defaultId` when it named it); `State` reads it back for `export` (model from `defaultModel`, base URL from `url` — a connection holds no context/output limits, so those never round-trip). `DefaultProviderID` recovers the provider behind the default connection for launch-time key injection. Written `0600`. **No secret is written** — see the lucinate config note below.
- `cmd/spinloop/fleet.go` + `metrics_render.go` + `status_render.go` — the `fleet` command group (`status`/`metrics`/`logs`/`dashboard`/`route`/`start`/`stop`): resolves the fleet file, fans out via `internal/fleet`, and renders. Observation is fleet-wide; `start`/`stop` are **single-node by contract** — with no node they list the fleet and touch nothing, because mutating every engine at once is a footgun. A node that fails is a rendered row (`unreachable`/`unauthorized`/`config-error`/`failed`), never a returned error: only a problem with the *fleet file* fails a command. `metrics_render.go` holds the renderers `remote metrics` and `fleet metrics` share, each caller supplying only its own heading; the split was made to keep `remote metrics` output byte-identical, so check that before changing them. `status_render.go` holds the shared status view both `remote status` and `fleet status` compute their overlapping facts (state, what it serves, last-active, version, uptime) from, so the two cannot word or compute them differently; each command keeps its own layout and its own extra facts (`base_url`/`healthy` for remote, the one-node-per-row table for fleet), and the change is deliberate — keep the shared facts single-sourced here while the layouts stay separate. Tests: `fleet_test.go` (stub daemons over `httptest`), `status_render_test.go`, plus the dockerised end-to-end example below.
- `cmd/spinloop/fleet_dashboard.go` + `dashboard_model.go` + `dashboard_render.go` + `dashboard_detail.go` — `fleet dashboard`: an interactive tiled view of the fleet, the CLI's first TUI (Bubble Tea + lipgloss — the only UI framework in the repo; `bubbles` was considered and dropped, overflow scrolling is the model's own row math, and `x/ansi` does the ANSI-aware line clipping). `fleet_dashboard.go` is the command layer: the `--fleet` flag, the non-TTY refusal (before the fleet file is even read — so a piped run fails identically wherever the file stands; the message names `fleet metrics --watch`, which stays the pipeable surface), `dashModelFor` (fleet-file resolution and the one-shot node build — an entry `Config.NewNode` refuses is a *standing* `OutcomeConfigError` the tile shows for the life of the view), and the alt-screen `tea.Program`. `dashboard_model.go` is the Elm model: **the tick is the cadence, the rounds are per node group** — local daemon machines refresh on the tick (2s), `kind: remote` environments on a 60-second deadline the model spends when it starts their round (a cloud status is a signed control-plane call, not a local socket, and a cold instance changes state on the scale of minutes); the grouping reads the fleet-file entry's kind, not the `Node` contract. A group's `FanOutNodes(MetricsCall)` round starts only when none of the group's is in flight — the tick reschedules itself whenever it fires (a one-shot `tea.Tick` without the reschedule leaves the board still after the second round, so do not simplify it away), a slow node shows an outcome this round and retries next, and answers arrive tagged with the group's generation, a superseded one discarded. `r` is due for every node, whatever the deadlines say. The program holds the model by **pointer**: Bubble Tea never reads a value model's `Init` back, so the first round's mutations (its generation, its deadline spend — real cloud calls, for remote environments) would be silently discarded. The actions are **per node, not per board**: each node carries a `dashAction` (the verb and the call's latest status line) beside its entry; `s` starts the selected node with no confirmation (fire-and-forget — the refresh rounds are the waiting, and a start carries **no** deadline, because a cloud wake takes minutes and a deadline would report a failure to a slow success), and a node already starting refuses a second `s` and an `x` without holding the other nodes — two cloud wakes run side by side. The footer's key help names the abort key only while a start is in flight on the node under the cursor (`canAbort`); `dashFooterHints` drops `"a abort"` from the static `dashGridKeys`/`dashDetailKeys` wording otherwise, since an abort with nothing to abort is a silent no-op — unlike a refused `s`/`x`, which at least explains itself on the status line. `x` opens the stop confirmation for the node under the cursor (footer prompt; `y` sends `Node.Stop`, `n`/escape send nothing), and a finished action clears only its own node and leaves its outcome in the footer status line, which carries outcomes only. A start's own progress is the one cross-goroutine conversation: a `kind: remote` start reports a line on every control-plane retry, and `remoteNode` implements the optional `fleet.ProgressStarter` (a plain `Node` verb plus a progress-carrying start; daemon nodes do not implement it — their start is one POST and one reply), so `beginAction` asserts for it and feeds the lines back through the model's `send` field — the `tea.Program`'s `Send`, safe from any goroutine and a no-op once the program has left, so a start that outlives the view reports into nothing rather than panicking. The lines land on `dashActionProgressMsg` and the in-flight tile renders the verb plus the latest line **beside** the node's last report — the call's lines say what the operator asked for, the report (state, serving, whatever a half-done boot already measures) says what the node is doing; a call that has not yet said anything, or a node no round has answered, shows the verb alone. `a` abandons the wait on the node's in-flight **start** only — `abortAction` refuses a stop in flight (verb must be exactly `"start"`), because a stop has no comparable open-ended wait and abandoning the dashboard's watch on it would leave the operator unsure whether it went through; this one guard is shared by the grid's `a` and the detail view's, so both narrow together: the action's own context is held on its `dashAction` beside the verb (`beginAction` creates it and runs the call on it, not on a background context), and the abort calls its cancel — the call's own loop returns on the done context, at the retry wait or mid-request, on the path it already has for a given-up wait, and its final message lands as for any finished action: the tile clears, the node may start or stop again, and the line says the wait was **abandoned**. The abort ends the wait, not the work: a cancelled client cannot take a wake the cloud is carrying back, so the line must never claim to have cancelled one, and a success that lands with the abort is still reported as the success (the line is about what the node did, not what the dashboard did); what the wake goes on to do comes back on the next refresh. Navigation is `j`/`k`/arrows in file order (no wrap), `r` a manual round, page keys the scroll row, `q`/Ctrl+C a clean exit. `dashboard_render.go` draws the frame: header, grid, footer — a grid row joins the *corresponding lines* of the tiles it places, because a tile is a multi-line block: joining the blocks glued the second tile's top border to the first tile's bottom border and shifted its body down a line (caught on a real three-node fleet). A tile is the **exact lines `fleet metrics` bar format prints** — `renderStatBars`/`renderTokenLines`/the last-active phrase are shared, not reimplemented — so the two surfaces cannot word a number differently; the tile content is computed as a plain string per `NodeResult` and each line hard-cut to 42 display columns (a cut, not a wrap: the bar block's alignment is load-bearing), then framed by lipgloss at 42×12 (a one-GPU running node fills it exactly). Keep that reuse — if a panel and `fleet metrics` disagree, one of them is wrong. Pause is deliberately absent: the `Node` contract has no `Pause` (see #119). `dashboard_detail.go` is the full-screen node detail view: `<enter>` on the grid opens it on the node under the cursor (`openDetail`, setting `dashModel.detail` — the cursor itself never moves, so the node in view is `entries[cursor]` for the life of the view) and `<esc>` closes it (`updateDetailKey`); `s`/`x`/`a` inside it drive that same node through the grid's own `beginAction`/`abortAction`; `q`/Ctrl+C are grid-only and do nothing here — quitting the dashboard from inside the detail view means escaping back to the grid first, a deliberate choice so a stray quit keystroke while inspecting a node cannot end the session — and the stop confirmation (keyed off `m.cursor`, unaffected by the mode, and carrying its own pre-existing `q`/Ctrl+C quit-mid-confirmation path unchanged) works unchanged in either. `View` dispatches to `detailView`, which draws three stacked sections at full terminal width: the metrics section is `dashNodeContentLines` — the tile's own content lines, factored out unclipped and unpadded so the tile and the detail view can never word a number differently — the log section is the node's engine log, tailed and followed the way `fleet logs -f` follows one node, and the footer names the view's own keys (`dashDetailKeys`), sharing `footerLine` with the grid so the confirmation prompt and a status outcome are worded identically. The log tail is its own poll, independent of the metrics refresh: `startDetailLogRound` runs `fleet.LogsCall` through `FanOutNodes` over the single node in view — keyed by the node's own `Name()`, not the fleet entry's, since that is the seam `LogsCall` itself resumes through — on a repeating tick (`detailLogInterval`, a test-hook variable like `dashboardRefreshInterval`) that reschedules itself only while the view is open on a node that could ever answer, which is the shutdown path (a stale tick landing after the operator switches to a standing entry must not resurrect a poll for it); a generation counter (`detailLogGen`, bumped on every open) discards a reply from a view since closed or reopened. The accumulated content is trimmed on every poll to what the pane can actually show (`detailLogCapacity`, from the terminal height less the header, footer and the three dividers around the sections), so a long session never grows an unbounded buffer, and a failed poll leaves prior content in place — the note (`fleetLogsNote`, the same wording `fleet logs` uses) only replaces it while there is nothing to show yet. An entry that never became a node (a standing config-error) opens straight to that standing outcome as the log pane's explanation, with no log round ever started. `f` pauses and resumes the tail (`detailLogFollow`): the tick chain keeps running for the life of the view regardless of the flag and only consults it to decide whether to actually start a round that tick, so pausing needs no teardown and resuming needs nothing but the flag flipping back — the one shutdown path stays tied to `m.detail`/node-liveness alone, not a second lifecycle for follow. The offset is left untouched while paused, so resuming is an ordinary poll from where the log already was: the engine's backlog since pausing is fetched and shown in one go, never silently dropped. The header names the state (`log: following`/`log: paused`) for a node that can poll at all, and says nothing for a standing node, which never polls regardless of the flag. Tests: `fleet_dashboard_test.go` — byte-stable tiles under a pinned colour profile, the layout table, the model driven directly with `KeyMsg`s over a fake in-memory `fleet.Node`, a `teatest` program-level run (the `dashboardRefreshInterval` and `dashboardRemoteRefreshInterval` vars are the test hooks), the CLI guards through the `cmdFleet` seam, and the detail view — enter/escape and the same start/stop/abort dispatch, the log tail accumulating and trimming across polls with `fakeDashNode`'s own `Logs` (mirroring `daemon.ReadLog`'s tail-with-limit and resume-from-offset shape), stale/superseded replies discarded, a stale tick not resurrecting a poll on a standing node, the follow toggle pausing and resuming dispatch and a `teatest` run confirming paused output is actually withheld and resuming delivers it, and a `teatest` run following the log pane growing and a start reflected in the metrics section before escaping back.
- `internal/fleet` — the fleet client. `Config`/`NodeConfig` parse `fleet.yaml` (unique names, default port from `daemon.DefaultAPIPort`, a `kind` of `daemon` or `remote`, defaulting to `daemon`); `Token` resolves a node's bearer token by env-var *reference* — environment then the `.env` beside the file — so the file never holds a secret, and an unset variable is a `config-error` naming it rather than a silent 401. `Client` calls one daemon's control API; the `Node` interface has two implementations: `daemonNode` (a machine on the network) and `remoteNode` (`remote_node.go`, a `spinloop remote` environment driven through its cloud control plane — `remoteNode` is a *thin wrapper* over the exported `remote.Status`/`Stats`/`Start`/`Stop`/`FetchLogs` calls, with the response→type mapping factored into pure functions so it is unit-tested directly rather than re-driving the signed client). Both return the same `daemon.StatusResponse`/`metrics.Stats`/`daemon.LogsResponse`, so the same fan-out and rendering pass over a local node and a remote environment. `remoteNode` also implements `ProgressStarter` — an optional interface beside `Node` (a node that starts with one POST and one reply has no situation to report and does not; callers that can show it, like the dashboard, assert for it) whose `StartWithProgress` passes the control plane's retry lines through `remote.Start`'s progress callback, and whose plain `Start` is the same call with the lines dropped. `FanOut` polls every node concurrently and returns one `NodeResult` per node **in file order**, so refreshes do not reshuffle rows; it is the fleet-file convenience over `FanOutNodes`, the package-level fan-out that runs over an explicit `[]Node`, which is the seam a mixed set (daemon nodes plus a remote environment) is driven through. `NewNode` is the one seam both `FanOut` and `fleet start|stop` build a node through, and it returns whichever kind the entry names: a `kind: remote` node's name is the registered environment (validated env-shaped — no `/`, no `.json`) and it has no `host`, so `validate` accepts it and `NewNode` returns a `remoteNode` loaded from `~/.config/spinloop/remotes/<name>/remote.json` — the control URLs never enter the fleet file, and a missing environment is a per-node `config-error` row, not a blanked view. A fleet of environments, or daemons and environments mixed, therefore observes and drives like any other; see `examples/fleet-remote` and `examples/fleet-mixed`. `select.go` and `wake.go` add routing: the ranking is pure (`rank`, over `[]NodeResult`) and the I/O is not, so the rules are testable without a network, and the package stays ignorant of Spinloops — the caller hands it a `Want` and a `remote.DeployConfig`.
- `examples/fleet-docker/` — a runnable multi-node fleet (real daemons in containers, a fake engine) that is also the fleet integration test, run per-PR by CI. Two details that are easy to break: the `llama-server` shim execs the Imposter **engine binary**, never `imposter up` (the CLI wrapper exits 0 when its child dies, so a crash assertion would pass while testing nothing), and the image pins `SPINLOOP_CONFIG_DIR` because a container has no useful `$HOME`.
- `cmd/spinloop/remote.go` — the `remote` command group (`start`/`restart`/`stop`/`status`/`deploy`), the CLI's only nested subcommand: each subcommand is a thin wrapper over `internal/remote`; `restart` is the composition of a pause-style stop (boot disk and weights survive, address unchanged) and the usual wake, blocking until the model serves again, and its `--force`/`-F` sends `force=true` to the stop endpoint so a wedged engine or daemon can be taken down without the graceful engine stop. `start` and `restart` both take the pre-warm choice as `--prewarm` (bare it enables, `--prewarm=false` disables); an absent flag sends no choice, so the cloud default (enabled) applies — the tri-state is what keeps "unset" distinct from "disabled" all the way to the daemon. `deploy` is the exception that carries logic: `deployConfigFor` turns a Spinloop (plus its preset) into a `remote.DeployConfig` — `PROVIDER` picks the runner (`llamacpp`/`vllm`; other providers are not self-hosted engines, so there is nothing to deploy), `MODEL` or the preset's `hf` names the weights as `repo:QUANT`, `CONTEXT` or the preset's `ctx-size` the window, `ALIAS` the served name, and the preset's remaining flags become `serveArgs`. The `[*]` globals are layered under the section (so `ngl`/`jinja` written there survive), and `cloudOwnedFlags` drops what the cloud sets itself (host/port/model/hf/api-key/ctx-size/alias/metrics), matched on `preset.CanonicalKey` so short aliases count. Config discovery (`resolveRemoteConfig`): an explicit `[path]` argument must name a Spinloop with a `REMOTE` instruction; with no argument, `./Spinloop` is consulted when present (its `REMOTE` resolved relative to the Spinloop, like `PRESET`), falling back to the per-user `remote.json`. Tests: `remote_test.go` (dispatch plus full flows against an `httptest.Server`, with `stubAWSEnv` pinning the AWS credential chain to static env credentials).
- `internal/remote` — controls the scale-to-zero GPU inference instance defined in [`remote/`](remote/) by calling its start/stop/deploy Lambda Function URLs (IAM auth, so requests are SigV4-signed via `aws-sdk-go-v2` — the repo's only AWS/network dependency). `Deploy` is the only call with a body, and SigV4 covers the payload hash, so `call`/`sign` take the bytes and hash exactly what is sent. `DeployConfig` deliberately carries no weights prefix: the Lambda derives the S3 layout and seeds the weights when they are absent, replying `{seeding, seedInstanceId}`. Config in `${XDG_CONFIG_HOME:-~/.config}/spinloop/remote.json` (`start_url`/`stop_url`/`deploy_url`/`region`/`base_url`), overridable via `SPINLOOP_REMOTE_*` env vars; `deploy_url` is optional so configs predating deploy still work for start/stop, and only `Deploy` complains when it is missing; `base_url` is optional too and no control call uses it — it is there so `apply` can point a harness at the endpoint without the Spinloop stating a `BASEURL` (see "Remote base URL" below); the region falls back to `AWS_REGION`, then to the region embedded in the Function URL host. `Start` retries while the endpoint reports 503/starting, honouring `retry_after_seconds`; the retain-until deadline and the start's pre-warm choice ride on it as query parameters, on every retry, since every retry is the same start.
- `internal/daemon` — the engine supervisor (`Supervisor`: at most one engine, started detached, its exit recorded rather than acted on — a crash is reported, never auto-restarted) and the HTTP control API `spinloop daemon` always exposes and `spinloop serve --api` opts into. Pre-warming the model's page cache is a **daemon option, not a config one**: `spinloop daemon --prewarm` wires `PrewarmModel` in (`prewarm.go`); a plain daemon on a laptop or a fleet node never pre-warms, and only the cloud AMI's unit passes the flag. The engine maps its weights and faults pages in as it copies them to the GPU, which a network volume serves at per-page latency rather than bandwidth, so the best-effort sequential read of the stored deploy config's model path — file or directory — gets ahead of the faults; it runs in a goroutine, never blocks a start, and a missing path is a silent no-op. A start may *decline* it — the deploy config's `prewarm` field (`*bool`) disables one for that start — but it can never *enable* it on a daemon that was not launched with the option, so the daemon's flag is the ceiling (`Daemon.Prewarm` is what a test records). Two things are worth knowing before touching it. **Routes live in one list**: `Routes()` in `api.go` returns every `"METHOD /path"` pattern with the schema its reply carries, and `Handler` registers from that list — a `ServeMux` cannot enumerate its own patterns, so this is what lets the contract be checked. **The contract is checked**: `docs/openapi.yaml` describes the API, and `openapi_test.go` compares it against `Routes()` and against the JSON tags of every struct the API serialises, failing the build when they disagree. Adding an endpoint means a line in `Routes()`, a handler, and a path in the spec; adding a response type means a line in the test's `schemaFor()` table. `activity.go` holds the other half of the daemon's job: it samples the running engine's token counters every 15 seconds and records when work last happened, which `/v1/status` reports as `lastActiveAt`/`idleSeconds` — the cloud's idle check reads that rather than judging activity from a single scrape of its own. `logging.go` holds spinloop's own diagnostic output: the level control (`ParseLevel`/`ResolveLevel`, `SPINLOOP_LOG_LEVEL`, `--log-level`) and the `summarize` middleware `Handler` wraps *outside* the auth layer, so a 401 and an unrouted 404 are recorded rather than invisible. **The logger is injected and a nil one discards** (`Daemon.Logger`, `Supervisor.Logger`, both read through `loggerOr`): the package holds no global, the CLI is the single place that decides where records go, and a directly-constructed daemon in a test stays silent — do not reach for `slog.Default()` here, which would make every existing test print. Severity is graded by outcome (2xx info, 4xx warn, 5xx error) so `--log-level warn` silences a polled fleet without silencing rejections, and no record carries a header or a body, so the token cannot leak through one.
- `internal/contextsize` — parses human-friendly sizes (`128k`, `1.5m`, `200000`); `Apply` sets `limit.context` and `limit.output` on opencode model blocks; `DefaultOutput` returns a quarter of the context (the fallback when `OUTPUT` is unset).
- `internal/preset` — parses [preset `.ini`](https://github.com/ggml-org/llama.cpp/blob/master/docs/preset.md) files into named sections of flags, and renders a server command for `serve` (`Parse`/`Flags`/`FormatCommand`). Parsing is engine-neutral; only the *spelling* of flags differs, which a `Dialect` carries (`LlamaCpp`, `OMLX`). The package-level `Flags`/`CanonicalKey`/`Preset.Args`/`Preset.Command` render LlamaCpp, so pre-dialect callers — notably `remote.go`'s `isCloudOwned` — keep their behaviour; `Preset.CommandIn` takes a dialect plus the engine's subcommand.
- `internal/catalog/providers.yaml` — externalised provider plumbing (URLs, key env vars, npm packages, a `pi:` block per Pi-capable provider, and a `lucinate:` marker per OpenAI-compatible provider usable by lucinate) — no model ids. **Add providers here, not in Go.** Embedded at build time but kept external for maintenance.
- `examples/` — runnable guides, each a directory with a README and a `Spinloop`.
- `remote/` — the cloud GPU deployment `spinloop remote` drives: a TypeScript CDK project (AWS Lambdas, EC2 Image Builder, S3 weights) with its own `package.json`, tests and docs, built and tested by pnpm rather than Go. It is the only non-Go part of the repository; CI runs its checks separately. **This repository is public, so nothing identifying a deployment — account ids, ARNs, Function URL hosts, allocated addresses, bucket names, resource ids — may be committed here or anywhere else in the repo.** `scripts/check-no-cloud-identifiers.sh` enforces that in CI; deployment state belongs in the gitignored files under `remote/` (`.env`, `remote.json`, `cdk-outputs.json`). `remote/Spinloop` is the exception that is **committed**: it says what to serve, is hand-maintained, and names no address — `pnpm write-config` generates only `remote.json`.

## Architecture notes (the important part)

**Harness routing.** `cmd` does the harness-neutral work (load the catalogue, validate the model, parse sizes, pick the provider) and then hands a `Selection` to the harness resolved by `harness.Resolve`. Each adapter owns its config format end-to-end. The import graph is one-way: `harness` imports `catalog`/`opencode`/`pi`/`contextsize`/`spinloop`/`config`; none of those import `harness`, and `config` sits at the bottom importing nothing, so there are no cycles. A model is keyed by its `ALIAS` when given, otherwise the provider-native `MODEL` (`modelKey` in `adapters.go`).

**Alias registry.** `spinloop alias` registers a Spinloop under a name, and `readSpinloop` — the single choke point `apply`/`unapply`/`serve`/`harness --spinloop` all share — resolves it, so one change gives every command the shorthand. Three rules hold it together. (1) The lookup is gated on the argument being *name-shaped* (`config.NameShaped`), so a path-shaped argument never causes a config read at all; that is what keeps `serve` working with no config of ours present, and what keeps the test suite off the developer's real config (a URL is never name-shaped either, for the same reason — it contains `/`). (2) A path on disk beats a registered name (`namesAnSpinloop` decides), so registering an alias can never change what an already-working command does; the shadowing is reported, not silent. (3) The registry stores the absolute path of the **file**, never the directory (a URL is stored verbatim — it is already unambiguous from any directory), so `serve`'s relative-`PRESET` resolution still lands next to the aliased Spinloop. A registered URL is never probed for liveness — not at registration beyond the one parse-time fetch, not by `resolveAlias`'s dangling check, not by `alias --list`/`show` — since that would cost a network call on every alias-resolving command; a stale URL simply fails where it is actually fetched. Under `harness`, the first positional is taken as a Spinloop only when no `--spinloop` was given, flag parsing was not terminated by an explicit `--` (`flagsTerminated`), and it names one; a `--` immediately after a *consumed* Spinloop is dropped, so every other command line is forwarded byte-for-byte.

**`SPINLOOP_ALIAS`.** The same registry, reached from the environment: `readSpinloop` consults it when it is handed no path at all, so the order is argument > `SPINLOOP_ALIAS` > `./Spinloop`. `spinloopFromEnv` resolves it rather than `resolveAlias`, and the two differ deliberately in both directions — a value it cannot resolve is an *error* naming the variable (an argument falls through to path handling), and a same-named file on disk does **not** shadow it (an argument's would). The reason is that an argument is usually a path and a variable can only ever have been set to name an alias; shadowing would make one export work in some directories and not others. Because the hook is in the empty-path branch, the variable decides *which* Spinloop is the default and never *whether* one is applied: a bare `spinloop harness` never calls `readSpinloop`, so it still launches unconfigured, while `harness -O` picks the variable up. `cmdAlias` opts out by passing `spinloop.DefaultFile` explicitly — registering must not resolve through the registry it writes to. `TestMain` in `cmd/spinloop` unsets the variable so a developer's export cannot reach the suite. **The gate to watch:** `resolveRemoteConfig` asks "is there a default Spinloop at all?" before calling `readSpinloop`, otherwise falling back to the per-user endpoint config. It asks `defaultSpinloopNamed`, which counts the variable as well as a `./Spinloop`; gating on the file alone silently skipped the variable and sent `spinloop remote status` to the `default` environment. Any future caller that tests for a default before reading one has to ask the same question. (`spinloop daemon` used to be a second caller of this shape — it no longer is; see "The daemon is a worker" below.)

**The daemon is a worker.** `spinloop daemon` has exactly two inputs: its flags and its API. It reads no Spinloop, no preset and no `fleet.yaml`, and takes no Spinloop path — one is refused rather than ignored. What a node runs comes from the start request's deploy config or the stored one; with neither, a start says so. This is what the cloud always did (its instances run `spinloop daemon --api-addr 127.0.0.1:4242` and are driven by pushed configs), and the reason to make it universal was that a node's Spinloop and a client's Spinloop are different documents — the fleet examples each needed a paragraph explaining that, and a node's `BASEURL` silently disabled routing for anyone who reused the file. The daemon's own bearer token therefore has three peer sources — `--api-token-file`, `SPINLOOP_API_TOKEN`, `--api-token` — since removing the Spinloop removed the `.env` it used to live in; two at once is a conflict, not a precedence. That a literal is allowed here and refused for the engine's key is a distinction, not an oversight: this token is configured locally by whoever runs the daemon, on a machine they have already decided to trust with it, while the engine's key is set remotely by a client and persists on the node. The `ps` trade-off is documented with the command rather than in the flag's help.

**The engine's key comes from the caller.** A start request carries it; a node sources none of its own. The client already holds the node's bearer token, so it can already run engine commands there and read logs full of prompts — a key is less than what it holds — and because it *sets* the key it knows the value to give the agent, so nothing has to reconcile two ends. Two invariants to keep: the key reaches the engine as `--api-key-file <path>` and never as a literal argument (a command line is readable by every local user; an engine with no key-file option is refused rather than gated that way), and it is never returned — no reply, error, or log line contains it. It persists beside the deploy config so a bare restart is gated the same way, and travels *with* the config it arrived with, so a new config carrying no key opens the engine rather than inheriting the last one. **Watch this one:** whether a key is required is the daemon's own fact (`storedEngineKeyPath`), not something to read back out of the argv — the endpoint is derived while the command is being built, *before* the key arguments are appended, so deriving it there reported a gated engine as open and a client picking up that node would send nothing.

**Fleet routing (`FLEET`).** A Spinloop's `FLEET` sends `spinloop harness` to a machine on the network instead of a local engine. The shape mirrors the `REMOTE` path deliberately — both answer "where does this agent send requests" — and it plugs into the same seam: `routeThroughFleet` runs inside `applyBeforeLaunch` *before* `applySelection`, fills `sel.BaseURL` from the chosen node, and the launch injects `OPENAI_BASE_URL` (plus the node's engine key) into the child. Four rules hold it together, each of which was chosen over a more convenient alternative:

- **A running engine is never stopped or restarted to make room**, including a pinned one. On a shared machine the cost of being wrong is someone else's session dying mid-request; the cost of the conservative rule is an error message. A node running a different model is therefore not a candidate, and waking only ever considers nodes that are *not* running.
- **The daemon reports its engine's port, never a URL, and never its key.** A daemon knows its engine binds `127.0.0.1:8080`, which is useless to anyone else, and it cannot know the name a client reaches it by. `EngineEndpoint` therefore carries parts (port, path, `loopbackOnly`, `requiresKey`) and `fleet.EngineBaseURL` composes them against the node's `host`. Authorisation to *drive* a node is not authorisation to be handed its engine's credential, so the key comes from the fleet file's `engineTokenEnv` instead.
- **Routing resolves before anything is written.** Same reason `fetchRemoteEnv` runs ahead of the apply: a failed route must leave the harness config exactly as it was, which is what makes routing safe to attempt automatically.
- **Readiness is the engine answering, not the daemon saying `running`.** The supervisor reports `running` when the process exists; llama.cpp then loads weights for minutes. `waitReady` polls status *and* TCP-probes the resolved endpoint. A timeout leaves the started engine running — it is probably still loading, and stopping it throws the expensive part away.

Waking reuses `POST /v1/start` with a deploy config in the body, so what a host can serve is decided by the daemon's existing `ValidateConfig` — there is no capabilities endpoint to drift from the validation that actually rejects things. The config comes from `deployConfigForNode`, which shares `deployConfigFor`'s derivation behind a `deployTarget` saying what the destination owns. Two things differ from the cloud, both because a fleet node is a machine the *operator* owns: no CONTEXT is required (that exists to size a cloud instance before provisioning, and a Spinloop `spinloop serve` runs happily should not need one added to be routed), and the preset's `host`/`port` survive. Dropping the bind — right for the cloud, which assigns its own — left every woken engine on llama.cpp's loopback default however the preset was written, so no other machine in the fleet could reach it and routing refused the node as loopback-bound. If you add a flag to `cloudOwnedFlags`, ask whether a node owns it too; `isNodeOwned` is that set minus the bind. `FLEET` and `REMOTE` are mutually exclusive at parse time; an explicit `BASEURL` wins over both, and routing says so rather than choosing a node it would then discard. A `FLEET` naming a URL is the gateway shape — it parses so the eventual gateway needs no new keyword, and fails today saying it is not implemented.

**URL-sourced Spinloops, and lazy `PRESET`/`REMOTE`.** A Spinloop path — argument, alias target, or `SPINLOOP_ALIAS` — may be an `http(s)` URL; `readSpinloop` fetches it via `internal/spinloopsrc` instead of `os.Stat`/`os.ReadFile`, with a URL ending in `/` getting `spinloop.DefaultFile` appended the way a local directory does. `PRESET` and a path-form `REMOTE` follow the same rule one level down: `spinloopsrc.Resolve(spinloopPath, value)` joins a relative reference against whatever kind of source named it (a local directory, or a URL with its own last path segment dropped), and an absolute URL value works regardless of what named it. The timing does not change from today's local-only behavior — `spinloop apply` never fetches `PRESET` (only `serve`/`remote deploy` do), and `spinloop serve` never fetches `REMOTE`; `apply` *does* still fetch a path-form `REMOTE` whenever one is set, URL or not, because `remoteEnvName` needs it to name the harness provider after the environment — only the separate `remoteBaseURL` fallback is skipped once `BASEURL` is already given. Nothing here is eager: parsing or resolving a Spinloop never fetches a `PRESET`/`REMOTE` reference by itself, only the command that already consumed it locally does so now over HTTP when the reference is remote. A URL-sourced Spinloop also has no local directory, so the `.env`-beside-the-Spinloop reads (`applySpinloopEnv` in `remote.go`, and `envFileDir` feeding `opencode.EnvResolver` in `main.go`) are skipped rather than attempted against a mangled path — only the Spinloop's own `ENV` instructions and the process environment apply. None of this reaches `spinloop daemon` — see "The daemon is a worker" above: every `spinloopPath`-shaped read described here (`applySpinloopEnv`, `resolvePresetPath`, `resolveRemotePath`, and URL support generally) only ever runs for `spinloop serve` (including `serve --api`, via `runServeForegroundAPI`, which still takes and reads a Spinloop — a Spinloop-URL there works exactly as it does for a plain `serve`) and the other Spinloop-driven commands; `spinloop daemon` itself takes no Spinloop path, local or remote.

**In-place JSONC merge, never overwrite (opencode).** This is the core invariant of the opencode adapter. Understand it before touching `internal/opencode`:

- Targets the existing `opencode.json` or `opencode.jsonc` (preferring whichever exists), falling back to creating `opencode.json`.
- Parses the config as **JSONC** via `github.com/tailscale/hujson` (tolerates comments and trailing commas).
- Edits are applied as an **RFC 6902 JSON Patch** on the hujson AST, which preserves comments and formatting *outside* the managed provider block. Parent objects (`/provider`) are only created with an `add` op when absent, so sibling providers are never clobbered. Path segments are escaped with `jsonPointerEscape` (model ids contain `/`).
- The `openrouter`-style block is deep-merged (`deepMerge`) over any existing one so user extras survive.
- `remove` guards every `remove` op with `Find` (RFC 6902 errors on missing paths) and clears the top-level default `model` when it pointed at something removed.
- Output is written `0600` (and `chmod`ed, since `WriteFile` won't change perms on an existing file) because it may hold an API key.

**Pi config (`internal/pi`).** Pi's `models.json` is plain JSON of the form `{"providers": {"<id>": {baseUrl, api, apiKey, models: [...]}}}`. The whole file is read into a generic map so unknown top-level keys, sibling providers, and unknown provider fields all round-trip untouched; only the managed provider is merged in (models unioned by `id`). `apiKey` is written as a `$ENV_VAR` interpolation (never the resolved secret), and **keyless local providers get a dummy literal placeholder** (`piPlaceholderAPIKey`) because Pi hides a provider's models from `/model` until *some* auth is configured. The reference is otherwise always written, even when the variable is currently unset, because Pi resolves it at run time — the key can be exported after the Spinloop is applied. The one exception is `apiKeyOptional` (see the traps below), where an unset variable means a genuinely keyless server rather than a key yet to be supplied. Pi has no top-level default-model setting, so `export` relies on the provider selection alone and `add` tells the user which model to pick.

**lucinate config (`internal/lucinate`).** lucinate's `connections.json` is plain JSON of the form `{"defaultId": "<id>", "connections": [{id, name, type, url, defaultModel, …}]}`, under `$LUCINATE_DATA_DIR` (else `~/.lucinate`, **not** XDG). spinloop maps a selection to one managed `openai`-type connection keyed by `spinloop:<providerId>` and points `defaultId` at it (lucinate's equivalent of a default model: `defaultModel` names the model, `defaultId` makes lucinate boot into it). The whole file is read into a generic map, so sibling connections and unknown fields — including an existing managed connection's `createdAt` — round-trip untouched; only the spinloop-owned fields (`type`, `url`, `defaultModel`, `name`) are overwritten. **No API key is written**, to `connections.json` or to lucinate's secrets store: lucinate reads an OpenAI-compatible key from `LUCINATE_OPENAI_API_KEY` when its stored secret is empty, and `spinloop harness` supplies it at launch — the same runtime-injection idiom opencode's `{env:VAR}` and Pi's `$VAR` rely on. Only OpenAI-compatible providers (those carrying a `lucinate:` marker) map; the rest error, like Pi's non-`pi:` providers. A lucinate connection has no fields for context/output limits, so `CONTEXT`/`OUTPUT` do not round-trip through `export`.

**Key/option resolution.** `catalog.BuildProviderBlock` sets `options.apiKey` (opencode) to the provider's `apiKeyEnv` as an `{env:VAR}` reference — never the secret — validating `apiKeyPrefix` and erroring when `apiKeyRequired` against the value it resolves. Resolution is `opencode.EnvResolver(dir)`: the environment first, then a `.env` **beside the Spinloop being applied** — an exported variable wins and the `.env` only fills a gap; `dir` is empty for a flags-only `add`, which falls back to the working directory. It deliberately is not relative to the binary or the source file (the old `runtime.Caller` form resolved to the build machine's path, so an installed binary never found one). The option is omitted only for a provider with no key variable, or an `apiKeyOptional` one at a local endpoint. Both harnesses therefore rely on the variable being set when the agent runs, which `harnessEnv` in the CLI arranges at launch. `optionsFromEnv` injects other options (e.g. `baseURL`, `region`) when their env vars are set. Both builders share `Provider.ResolveOptions` for that and `Provider.RequireOptions` for `optionsRequired`, deliberately: when only the opencode builder applied them, a per-provider variable like `OLLAMA_BASE_URL` was silently dropped under Pi, which then handed a *remote* server the keyless placeholder because `IsLocalEndpoint` still saw `localhost`. The opencode top-level `model` is `<providerId>/<modelKey>`. Base-URL precedence for both builders: `--base-url`/`-u` flag > `SPINLOOP_BASE_URL` > the provider's own `optionsFromEnv` variable > the catalogue's `pi.baseUrl` (Pi only) > `options.baseURL`.

**Remote base URL.** A Spinloop is user-managed, so nothing generates or rewrites one — which is why a Spinloop for a remote endpoint states no `BASEURL`: the address is deployment state, and the deployment (`remote/`'s `pnpm write-config`) records it as `base_url` in the `remote.json` its `REMOTE` names. `applySelection` fills it in from there, and only when the Spinloop stated none, so a hand-written `BASEURL` always wins; `remoteBaseURL` (`cmd/spinloop/remote.go`) reads the file leniently, since a Spinloop may name a remote config before the deployment that writes it exists. `serve` deliberately does not do this — it binds from `BASEURL`, and a remote address is not something to bind to.

**Local environment.** Precedence is the same everywhere spinloop resolves local variables: `ENV` keyword > process environment > `.env` beside the Spinloop — an exported variable wins and the `.env` only fills a gap. Two paths apply it:

- The `remote` control commands (`deploy`, `start`, `stop`, `status`, `stats`) call `applySpinloopEnv` (`cmd/spinloop/remote.go`) before resolving config or doing any AWS work. It loads the Spinloop's local environment into the *process* environment — it must be `os.Setenv`, not a lookup closure, because the AWS SDK's credential chain reads `os.Environ()` directly. The `.env` fills only gaps (`opencode.ParseEnvFile` + `os.Getenv(key) == ""`), then each `ENV` line overrides.
- `spinloop harness` builds the launched agent's environment instead of mutating its own: `harnessEnv` starts from `os.Environ()` and adds resolvable provider keys, then `overlayLocalEnv` (`cmd/spinloop/main.go`) layers the whole adjacent `.env` (gap-fill) and the Spinloop's `ENV` (override) onto the child's `cmd.Env` only. No Spinloop active means no overlay. For the **lucinate** harness one more variable is added afterwards: `lucinateLaunchKey` resolves the active provider's key (the active Spinloop's provider, else the one behind lucinate's default connection via `lucinate.DefaultProviderID`) and `setEnvIfAbsent` places it as `LUCINATE_OPENAI_API_KEY` — so a connection whose secret spinloop deliberately left unwritten can still authenticate, and an explicit setting already in the child's env wins.

`ENV` is local-only: it never enters `remote.DeployConfig`, so nothing reaches the instance (`deployConfigFor` builds the payload from Spinloop fields alone), and on the harness path it shapes only the child. `EnvResolver`'s process-env-first rule now matches this precedence — the earlier `.env`-first inconsistency is resolved, so keep the two paths aligned if you touch either.

**`serve`.** `spinloop serve` launches a local inference server for a Spinloop without touching any harness config. The engine comes from `PROVIDER` via `engineFor` (`cmd/spinloop/serve.go`), the local twin of `runnerFor`: `llamacpp` runs `llama-server`, `omlx` runs the Apple-Silicon oMLX CLI, and anything else is an error. A `serveEngine` carries the binary, any subcommand, the preset dialect, the Spinloop→flags mapping, and the install hint. With a `PRESET` it flattens the matching `.ini` section (plus `[*]` defaults) into flags in that engine's dialect; otherwise it derives a command from the Spinloop alone. Anything the Spinloop states overrides the preset. `--dry-run`/`-n` prints the command without running it. oMLX serves a whole `--model-dir` and picks per request, so only `BASEURL` becomes a launch flag for it, and it starts happily with neither `PRESET` nor `MODEL`. `serve` never resolves or passes an API key — it prints the command it runs.

Invariants to keep: opencode merges stay idempotent and never drop unrelated config or comments; Pi merges preserve sibling providers and unknown fields, and lucinate merges preserve sibling connections and unknown fields; no harness ever writes a resolved secret to disk (opencode `{env:VAR}`, Pi `$VAR`, lucinate leaves it to `LUCINATE_OPENAI_API_KEY` at launch); output stays `0600`; the harness never appears in a Spinloop, and neither does an alias — both are machine-local, so a Spinloop stays portable; spinloop's own `config.json` is only ever written read-modify-write, so a new setting cannot clobber an existing one; `__complete` never returns an error and never writes to stderr, whatever the state of the config or catalogue.

## Traps

These are mistakes already made here; each was silent rather than loud, which is what makes them worth writing down.

**The catalogue is embedded at build time.** `providers.yaml` is `//go:embed`-ed, so a previously-built `spinloop` binary keeps applying the *old* catalogue no matter what the file says. Rebuild before testing any catalogue change, or you will "verify" a fix that is not in the binary you ran. (`--providers`/`SPINLOOP_PROVIDERS` reads a file at run time and sidesteps this.)

**A preset section is not the whole preset.** `Preset.Select` returns only the named `[section]`; the `[*]` defaults live separately in `Preset.Global`. Anything that consumes a section's `Params` directly — rather than going through `Args`/`Command`, which layer both — silently drops whatever the user put in `[*]`. That is usually the settings they consider obvious enough to write once, like `ngl` and `jinja`, so the failure surfaces later as a model running on CPU or refusing tool calls.

**Match preset flags by canonical name.** Preset keys have short aliases (`ngl` is `n-gpu-layers`, `c` is `ctx-size`, `hf` is `hf-repo`, `a` is `alias`). Comparing raw keys against a list of flag names therefore matches only the spelling you happened to think of. Use `preset.CanonicalKey`, which is exported for exactly this; `Flags` already dedupes layers by canonical name, last layer winning.

**A preset dialect is not interchangeable.** `internal/preset` parses any INI the same way, so an oMLX preset fed through llama.cpp's dialect parses cleanly and produces a *wrong* command: the alias table rewrites `m` to `--model` and `c` to `--ctx-size`, and the boolean table drops a `key = 0` entirely. Nothing errors — the server just receives flags it does not accept, or silently loses a setting. The dialect always comes from the engine `PROVIDER` names, never from the file.

**A busy engine does not answer its own metrics endpoint.** llama.cpp serves `/metrics` from the same queue it serves inference from, so a scrape taken while a prompt is being processed waits for that prompt to finish — tens of seconds on a long context. `/v1/metrics` used to scrape inline, so the handler blocked for as long as the engine had work, and `spinloop fleet metrics` (5s client timeout, against a handler whose scrape timeout was also 5s) could not win that race: the view went blank exactly when there was something worth watching, reporting the node as `unreachable`. The counters now come from the background sampler's last reading (`engineSample`), which the daemon takes every 15s regardless of who is asking — so the handler never waits on the engine, and staleness is bounded by the sample interval. Three things to preserve if you touch this: the *cached scrape error* is still reported, because silently omitting the token block is what once hid a scraper pointed at the wrong port; the sample is forgotten on start, so one engine's counters are never reported against the next; and the sampler retries at `catchUpInterval` (1s) until a reading lands, dropping to the full interval only afterwards — without that, a freshly started engine reports no counters for up to 15s, which is exactly the window someone watching a node they just started is looking at.

**An exported-but-empty variable is a gap, not a choice.** `setEnvIfAbsent` keys on the variable being *present*, so an `OPENAI_BASE_URL=` in the environment counts as set and suppresses the value routing meant to supply — leaving the agent pointed at nothing. `setEnvIfBlank` is the one to use for an address or a key, matching what `harnessEnv` already does for the remote endpoint's values; the distinction only shows up when something exports an empty string, which shells do more often than you would think.

**`contextsize.Parse` is decimal.** `128k` is 128000, not 131072 — a `CONTEXT` written that way is not the power-of-two window it looks like. It also *overrides* a preset's `ctx-size` (both in `serve` and in `remote deploy`), so the Spinloop, not the preset, decides the window whenever it states one.

## Workflow

Warn the user if they are going to merge a branch with un-archived openspec changes.
